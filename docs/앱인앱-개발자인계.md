# 드림그룹 앱인앱(웹뷰) 연동 — 개발자 인계 자료

> 목적: 애돌(최애돌) 앱 안에 **드림그룹을 앱인앱(웹뷰) 게임**으로 얹을 때,
> ① 로그인 유저만 진입시키는 **허들(인증)** 과 ② 그 유저의 **최애 아이돌 정보**를 웹게임에 넘기는 방법.
> 애돌 **본체 코드/DB/동선은 건드리지 않고**, 기존에 이미 깔려 있는 길을 재활용하는 것이 원칙입니다.

작성일 2026-07-27 · 소스 기준 커밋: idol_ios `d4e805da6` / idol_android2 `b6125289` / idol_realserver_source `0e3cad7e2`

## 0. 요약 — 이미 절반 이상 깔려 있습니다

| 필요한 것 | 현황 | 재활용/신설 |
|---|---|---|
| 앱 안에서 웹게임을 웹뷰로 띄우기 | **iOS·안드 모두 이미 구현** (`GameWebView`/`GamePortal`) | ✅ 재활용 |
| 웹뷰에 유저정보 URL/헤더/JS로 주입 | **이미 함** (닉네임·언어·테마·하트잔액) | ✅ 재활용 |
| 로그인 유저만 통과시키는 인증 | 웹용 **JWT 발급 API `web_token` 이미 존재** | ✅ 재활용 |
| 외부 웹서비스에 유저 신원 안전하게 넘기기 | **C:Z9 SSO 선례 존재** (RS256+JWKS 완성형) | ✅ 복제 |
| 웹게임용 "최애 조회" API | 없음 (기존 self API는 앱 전용 인증) | ⏸️ **선택** (있으면 편의, 없어도 됨) |
| 웹게임용 권한 스코프 | `web:recommend:read`만 있음 | ⏸️ 최애 API 붙일 때만 추가 |

> **범위 결정(2026-07-27):** MVP는 **"로그인 유저만 통과시키는 인증(허들)"만 필수**로 합니다.
> 최애 정보 연동은 **편의성 옵션** — 나중에 얹어도 됩니다. 발급되는 JWT 안에 이미 `sub`(user_id)가 있어
> 유저 식별은 확보되므로, 최애 조회 API는 필요해지는 시점에 추가하면 됩니다.

**즉, 지금 필수 신설 작업은 사실상 없습니다** — 기존 `web_token`(JWT) 발급/검증을 재활용해 "애돌 로그인 유저인지"만 확인하면 됩니다. 클라이언트도 URL/헤더에 토큰 한 줄 추가하는 수준입니다.

## 1. 전체 그림 (권장 아키텍처)

```
[애돌 앱]                              [드림그룹 웹게임]              [애돌 서버]
   │  ① Basic 인증으로 웹토큰 요청                                       │
   │  GET /api/v1/users/web_token/  ───────────────────────────────────▶│
   │◀──────────────────────  1시간짜리 JWT(aud=web) 반환 ───────────────│
   │                                                                     │
   │  ② 웹뷰로 게임 오픈 + JWT/최애 전달                                  │
   │  (기존 GameWebView URL/헤더 주입 자리 재활용)  ──▶ [웹게임 로드]      │
   │                                        │                            │
   │                                        │ ③ JWT로 최애/게임데이터 조회 │
   │                                        │  Authorization: Bearer JWT  │
   │                                        │  GET /api/v1/users/most/ ──▶│ @auth_jwt 검증
   │                                        │◀──── 최애 정보 반환 ─────────│
```

- **허들(로그인 유저만)** = ②에서 JWT 없는/비로그인 접근은 웹게임 서버가 거부.
- **최애 몰입 연동** = ③에서 JWT로 최애 정보를 받아 "내 최애 센터" 구성.
- 애돌 본체 경제(하트)·랭킹은 **건드리지 않음** (읽기만, 쓰기 금지).

> 보안: **토큰은 URL 쿼리보다 헤더/postMessage로 전달** 권장(URL은 웹 접근로그·리퍼러에 남음).

## 4. 서버 재활용 지점 (`idol_realserver_source/`) — ★가장 중요

### ✅ 그대로 재활용 (신설 불필요)

**(1) 웹용 JWT 발급 API — 이미 존재**
`GET /api/v1/users/web_token/`
- 리소스 `api/users/resources.py:5260` · 로직 `api/users/facades.py:158`
- 앱이 Basic 인증으로 호출 → **1시간 TTL JWT(aud="web") 발급** (docstring에 "일회성" 명시)
- JWT 구현 `utils/jwts.py` (`create_access_token:43` / `verify_access_token:76`)

**(2) 웹 JWT 검증 데코레이터 — 이미 존재**
`@auth_jwt(scope)` — `api/views_common.py:326` (`_auth_jwt:300`)
- 게임 API 메서드에 이 데코레이터만 붙이면 `request.user` 자동 세팅
- 실사용 예시(그대로 따라 만들 템플릿): `api/recommend/resources.py:50` `@auth_jwt("web:recommend:read")`

**(3) 외부 웹서비스에 유저를 넘기는 완성형 선례 — C:Z9 SSO ★**
`api/auths/services.py Cz9SsoService`
- 최애돌이 **IdP(신원 발급자)**, 외부 서비스가 **검증자**. RS256 서명 id_token + JWKS 공개.
- 발급 `POST /api/v1/auths/sso/cz9_token/` (`api/auths/resources.py:44`)
- 검증용 공개키 `GET /api/v1/auths/jwks/` (`api/auths/resources.py:37`)
- id_token에 nickname·login_provider·profile_image_url·locale 등 포함 (`services.py:56~`)
- **드림그룹이 자체 백엔드를 갖는다면 이 SSO 패턴을 복제하는 것이 가장 안전** (대칭키 공유 회피).

### ⚠️ 신설 필요 (경량)

**(4) 웹게임용 최애 조회 API**
- 기존 `GET /api/v1/users/self/` (`api/users/resources.py:1520`, 최애 전체 반환)는 `@auth_mirror`(앱 Basic 전용)이라 JWT로 못 부름.
- → `@auth_jwt("web:game:read")` 를 단 **경량 신규 엔드포인트**(예: `GET /api/v1/users/most/`) 추가. 내부에서 `request.user.most`만 뽑아 반환.
- DTO/facade 구성은 모범 모듈 `api/recommend/`, `api/charts/` 따라가면 됨.

**(5) 스코프 1개 추가**
- 현재 `web_token`이 주는 scope는 `["web:recommend:read"]` 하나뿐 (`facades.py:164`).
- `web:game:read` 를 여기에 추가하고, (4)의 데코레이터와 짝 맞춤.

### ⚠️ 유일하게 확정 필요한 것 — "JWT를 어디서 검증하나" (작업 #3)
로그인 허들만 남으니, 남는 실무 결정은 **드림그룹의 백엔드 구조** 하나뿐입니다. 드림그룹 프로토는 현재 **Firebase(BaaS) 기반**이라 자체 검증 서버가 얇습니다. 두 갈래:
- **(a) 드림그룹이 자체 서버/Cloud Function 있음** → C:Z9 SSO 방식(RS256 + `GET /api/v1/auths/jwks/` 공개키 검증)을 그대로 복제. 키 공유 없이 안전. **권장.**
- **(b) 순수 프론트(정적 웹앱)만** → 토큰을 검증할 곳이 없음. 이 경우 애돌 서버에 "이 토큰 유효한가?" 확인용 경량 엔드포인트가 하나 필요하거나, Firebase Function에서 JWKS로 검증. 이 갈래는 개발자와 방식 합의 필요.

## 6. 지켜야 할 선 (설계 가드레일)

- 최애 정보는 **읽기만.** 본체 하트·투표·랭킹에 **쓰기 금지** (앱인앱 격리).
- 실존 아이돌 **사진 원본은 변형 금지** (이펙트는 카드 프레임/배경에만). "유저 창작 콘텐츠" 명목은 시스템이 이미지를 가공하는 순간 끊길 수 있음.
- 실존 아이돌 **능력치 수치화·서열화 금지** (명예/팬덤 리스크, UGC로 안 덮임).
- 토큰은 **헤더/postMessage 전달** 우선(URL 쿼리 지양).

## 7. 개발자에게 확인할 질문

1. **(핵심)** 앱인앱 웹게임의 로그인 검증은 **기존 `web_token`(JWT) 재활용**으로 가면 될까요? 그리고 드림그룹이 이 토큰을 **어디서 검증**하는 게 좋을까요? — (a) 자체 Cloud Function에서 JWKS 공개검증(C:Z9 방식 복제) vs (b) 애돌 서버에 토큰확인용 엔드포인트 신설.
2. 웹토큰 TTL 1시간인데, 게임 세션이 길어질 때 **갱신(refresh)** 은 어떻게 처리할까요?
3. **(나중에)** 최애 정보 연동을 붙일 때는 `@auth_jwt` 신규 엔드포인트 + `web:game:read` 스코프로 여는 걸로 괜찮을까요? — MVP엔 불필요, 옵션.
